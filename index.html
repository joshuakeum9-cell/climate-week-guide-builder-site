What this is

The guide's value is not that it is comprehensive

A climate week throws hundreds of events at people, and the official site lists a fraction of them. The guide's value isn't that it's comprehensive. It's that it has a point of view and makes the week navigable.

That distinction shapes the whole pipeline. The curated sections, Top Hits and the per-category Highlights, are where the point of view lives. The All Events lists underneath them are the repository, so nothing gets lost. The plugin builds both, from one dataset, so the numbers never disagree between sections.

This page is for a chapter lead who has just installed the plugin and has never run it. It covers what you need before you start, what the plugin will ask you for, where it stops and waits, and what comes out at the end.

Prerequisites

Before you start

Run this in Claude Cowork, not in chat. The pipeline writes files to disk as it goes, runs scripts, builds a Word document, and drives the Airtable and browser connectors. A plain chat window cannot do any of that, so the run cannot complete there. Everything below assumes Cowork.

Four things. The second one has no workaround, so check it before you begin rather than halfway through Stage 0b.

A Luma calendar URL

The city's climate week calendar, at luma.com/<handle>. This is what the events get scraped from.

The Claude-in-Chrome extension

A hard requirement, with no fallback. Luma's pages are JavaScript-rendered, and its API only accepts calls from a luma.com origin, so plain fetching returns an empty shell.

An Airtable account with the MCP connector enabled

Used for the events base and the public submission form built in Stage 1c.

Roughly an hour of your own attention

Spread across the run, at the human checkpoints in the pipeline below. Not one continuous hour.

The one that matters

Why Stage 1b deserves your attention

The approved spreadsheet becomes the schema for the Airtable base. Once that base is published, the structure is frozen and reused for every future city. An error you wave through at Stage 1b propagates forever.

It is also the only step in the pipeline that stops dead. Everything before it is preparation and everything after it is writing. If you are going to give the run your full attention once, give it here.

Inputs

What it asks you for, and what it never asks

Chapter leads get anxious about being asked for things they do not have. Here is the concrete list, in both directions.

It will ask for

  • Byline names and each person's Substack profile URL
  • Sign-off names and each person's LinkedIn URL
  • The official week website and the official submit page
  • The host city's own chapter Substack URL
  • Confirmation before folding a thin category
  • Consent before publishing the public submission form
  • Optionally, writing samples so the prose sounds like you

It never asks for, because these are already inside the plugin

  • The 26 category cover images, Nicole Kelner artwork, bundled as real files
  • The volunteer and start-a-chapter Airtable form
  • The nine other chapter URLs, the two Streetlife typeform links, and Nicole's artist links
  • The events view and submission form links, which Stage 1c generates
Anything you cannot supply becomes a bracketed placeholder. It is highlighted yellow in the Word document and listed in a MANUAL-INPUTS.md register that ships with every guide. Nothing is silently invented, and no plausible-looking URL is ever made up to fill a gap.

Output

What you get

Four artifacts. The distinction between the first two is the thing people get wrong, so it is worth reading before you publish rather than after.

  • guide.htmlthe publishing file

    Open it in a browser, select all, copy, and paste into Substack. Formatting and images survive intact. Images are inlined as base64 at 800px, so the file is self-contained: 23 MB of source PNGs becomes about 2.3 MB.

  • guide.docxarchival and shareable

    Embedded hyperlinks on every event title, a cover image at the top of each category section, and every unfilled placeholder highlighted yellow so it is visible while scrolling.

  • MANUAL-INPUTS.mdthe register

    Every slot still needing your attention: where it sits in the guide, and what it currently says.

  • CHECKPOINT.mdthe resume file

    Progress and settled decisions, so a fresh session can pick up where the last one stopped without redoing work.

Why HTML rather than markdown

This is the single most useful practical tip on the page. Substack's editor is rich-text, and it reads rendered HTML off the clipboard. It does not parse markdown on paste. Paste the markdown and you get the literal ## and > characters on screen, leaving every link and every image to be rebuilt by hand across a hundred pages.

The round trip that works
markdown source  →  rendered HTML file  →  open in browser  →  select all + copy  →  paste

markdown source  →  paste
                     literal ## and > characters
One known limitation. Substack re-hosts pasted images on its own CDN, which usually works but occasionally drops one on a large paste. After pasting, scroll the draft and confirm the category images all landed before you publish. Any that did not can be re-added from the output folder, which keeps the full-resolution originals.

Editorial

The house rules

There are more than these. These are the ones that shape what the output actually reads like.

Descriptive, never commentary

Category descriptions say what an event is, not how good it is. No "worth attending", no "don't miss", no "the standout". Curation is expressed by what gets included, not by telling the reader it is good. The editorial voice lives in Top Hits, which is deliberately conversational; the category body is not.

Commentary, never This is a must-attend for anyone serious about CDR.
Descriptive, always Isometric hosts a full-day summit for CDR buyers, suppliers, investors, and policymakers working through what defines quality and which financing structures hold at scale.

The tell is any sentence that could be a review. The fix is to cut it and state the fact underneath.

No em dashes

The house substitute is a spaced hyphen. It is not a stylistic preference applied loosely: the shipped guides carry 935 spaced hyphens in NY 2025, 82 in PNW, 49 in Chicago, and 28 in London. A comma, a colon, or a restructured sentence is equally fine.

Structural variety

No two descriptions in a category may open or close the same way. Closing on a logistics note is fine once and grating three times in a row. Banned outright: any recurring closer template of the "This event suits X people" kind.

Heading hierarchy is exact

Title is #. The welcome one-liner is ###, and it is the only unbolded heading in the document. The category name, its Highlights header, and its All Events header are all ## as siblings, which is the piece people get wrong most: Highlights is not a child of the category. Top Hits day buckets are ####. Highlight descriptions sit inside > blockquotes.

Categories come from the data

The 26 are a ceiling, not a target. No Finance events in the spreadsheet means no Finance section, and a count is never carried over from a previous city. A category holding fewer than three events gets folded into wherever its events' own secondary categories point. It is never dropped, because dropping it would lose events.

US spelling by default

London is the single exception and publishes in British English.

Confidence

Quality gates

Eleven automated gates run before anything ships. Most of them are unremarkable sweeps. These are the sharp ones, and each exists because something got past a human once.

Category number agreement

The category count has to match across all four places it appears. This gate exists because the Chicago 2026 guide shipped with "26 Categories" in its contents and 24 everywhere else.

Adaptation-leftover sweep

Scans for another city's names surviving an adaptation. Same guide: "How to LCAW" appeared in a Chicago guide, carried over from London.

Every event survives a fold

A fold relocates events, it never removes them. The gate checks the post-fold set against the source of truth rather than trusting the operation.

Images resolve and are unique

Every image link has to resolve, and no category may reuse another category's artwork.

Blockquote count equals highlight count

A cheap check that catches the most-missed piece of markup in the whole spec.

And six more

Hard-rule sweeps, fabrication and self-plagiarism checks, placeholder reconciliation, link checking, cross-section count reconciliation, and a final voice and city-specificity read.

Recovery

When things go wrong

A long run can lose its sandbox. This has happened in production, after the Airtable base was built but before any prose existed. The pipeline is built around that being survivable rather than around it not happening.

What a crash actually costs you

Artifacts are written to disk as they are finished, one file per category rather than one file at the end. So a crash costs the section in progress, not the run. If twenty-five categories are written and the twenty-sixth dies, you lose the twenty-sixth.

What keeps working when the sandbox dies

The Airtable connector and the browser do not depend on the sandbox. Base creation, row import, and link capture all still work when it dies. That is why Stage 1c tends to survive incidents that take out the writing stages.

How to resume

Start a fresh conversation. Attach events.csv and CHECKPOINT.md. Say which stage to resume from, and say that the base already exists.

That last part matters. The plugin will not recreate an existing base, and you do not want it to: a second base means a second public form, while the first link may already be circulating.
